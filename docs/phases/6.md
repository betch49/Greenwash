# Phase 6 — Scorer, confidence, `ai_share` guard, methodology page

Builder note, 2026-10-21.

## What was built

**Weights (`config/weights.json`, read only through `src/lib/score/weights.ts`).** Axis weights 25 / 25 / 30 / 20, points per signal kind for every kind the pipeline emits, caps per axis, the claims-rate parameters, `defaultWeightHint`, the Phase 5 `regulatorRuling` section (unchanged), the LLM guard (`maxShare` 0.5), label thresholds, and the confidence rules (which step ids feed which axis). A zod schema rejects negative points, axis weights that do not sum to 1, and `maxShare` above the brief's 0.5. `DEFAULT_WEIGHT_HINT` (claims engine) and `REPAIR_WEIGHT_HINT` (repair) now read `defaultWeightHint`; `rulingWeightHint()` reads the validated file.

Points chosen (all in the file, all shown on /methodology):
- claims: `claim.unsupported` 1, `claim.supported` 0.25 (strictly fewer, ADR-015). Sub-score = points per 1,000 visible words (at least 1,000 words counted) × 15, capped at 100.
- evidence: `no_report_found` 40, `stale_report` 25; `report_found`, `report_found_undated`, `absolute_emissions_found`, `supplier_list_found` 0 (protective).
- track: `claim.removed` 20, `regulator.ruling` 25 × the Phase 5 hint (upheld × 2, within 3 years × 1.5).
- repair: `no_repair_info_found` 50 (moderate, Phase 5 review); every protective repair kind 0, so `ifixit_guides` ≤ manual / parts (ADR-018; see C-4).
- labels: Moderate from 25, High from 50.

**Scorer (`src/lib/score/scorer.ts`).** Receipt check first (dev throws `ReceiptError`, prod drops and logs). Points = kind points × `weight_hint` (unknown kind or negative hint ⇒ 0). Claims axis input is the run's ClaimStats (ADR-015: repeats count; unsupported and supported matches at their points), with LLM claim signals added by their own points; without ClaimStats the rule-based claim signals count once each. Sub-scores capped, weighted sum, rounded. `not_applicable` repair ⇒ weight redistributed in proportion (Oatly: 31.25 / 31.25 / 37.5). Label, "Based on N verified signals from M sources." (M = distinct hosts).

**Confidence (`confidence.ts`).** Share of effective axis weight whose axis has data: one of its steps `done` (not skipped) **and** at least one receipted signal on it (track also counts an archived snapshot read). Combines deliverable 2 ("no signals ⇒ lowers confidence") and deliverable 3 ("step done with data"). Not-applicable axes never lower it.

**AI share (`ai-share.ts`, ADR-007).** Per axis, the non-LLM sub-score is computed from non-LLM signals alone; LLM points are what LLM signals add on top. Score = min(Σ w × sub-score, non-LLM points ÷ (1 − maxShare)). Both terms only fall when a signal is removed, so the guard is monotone; `ai_share` = LLM points ÷ score ≤ maxShare by construction (also clamped); no non-LLM points ⇒ LLM signals add nothing and `ai_share` = 0. `llm_signal_ids[]` in every report.

**ReportV1 (`report.ts`, zod) and persistence.** `{ version, run_id, brand, website, score, label, label_text, confidence, ai_share, llm_signal_ids, basis, axes[{id, weight, effective_weight, status, subscore, signals}], timeline, could_not_check, skipped, generated_at, sources_count, signals_count }`. `runPipeline` records `step_status` by step id, builds the report on a done run and stores it with `ReportsRepo` in the existing `reports` table (`PipelineOutcome.report`, `report_id`). **Failed runs now persist their could-not-check lines and timeline** (Phase 4 review carry-forward); no report is built for a failed run.

**UI.** /analyse shows, for a done run, "Score N, confidence M%", the label, "AI contributed to X% of this score", the basis line and a link to /methodology (the full report UI is Phase 8). `/methodology` renders the axis-weight, points and parameter tables from `weights.json` and the rest of `docs/METHODOLOGY.md` (small dependency-free Markdown renderer; Section 7 is replaced by the generated tables). Header nav link to /methodology. Every string is in `wording.ts`.

**Docs.** METHODOLOGY Section 7 is generated by `weightsMarkdown()` (`src/lib/score/methodology.ts`) and must equal it; new Section 11 "From signals to a score". LIMITATIONS gains "Score and confidence". CHALLENGES C-4.

## Skipped / deviations, and why

- **Protective kinds carry 0 points** instead of lowering a sub-score: lowering on presence contradicts 6.2 (C-4, director to rule). The ADR-018 ordering therefore holds only non-strictly.
- **Claims axis from ClaimStats**, not from deduplicated claim signals, as ADR-015 requires; the per-kind points still decide the worth of a supported vs unsupported match.
- **`signals` table not written**: ReportV1 holds the signals; the table stays for Phase 8 if needed.
- **No report for a failed run**: only its outputs (could-not-check, timeline) are persisted.

**C-4 ruling (ADR-020).** The builder's resolution is correct and adopted: points are risk points only, protective kinds carry 0 and lower a sub-score by replacing the risk kind; `ifixit_guides ≤ manual ≤ parts` holds non-strictly. The two inert evidence kinds and the iFixit-only case go to `docs/LATER.md` as receipted absence kinds (a Phase 3/5 rule change plus re-pinned fixtures; not spent as a re-plan).

**Judgments on the points the orchestrator raised.**
1. *`ai_share` guard is a genuine property test.* `randomSignals` draws kinds from `Object.keys(WEIGHTS.points[axis])`, so any kind Phase 7 adds to the file is exercised automatically; `llm_used` is randomised per signal including all-LLM sets, hints are randomised (covers the Phase 7 "unsure ⇒ hint halved" path), the bound is asserted against the literal 0.5 rather than the config value, the schema refuses `maxShare > 0.5`, and the test demands > 100 cases with `ai_share > 0` so the bound cannot pass vacuously. A configuration or guard change that let LLM points exceed half the score would fail it. Phase 7 carry-forward: LLM-accepted claim sentences must **not** also be counted in `ClaimStats` (the scorer adds LLM claim signals on top of the stats; double counting would understate `ai_share`), and 7.6 must show `ai_share > 0` for Northwind.
2. *N/A weight redistribution is consistent with the brief.* Not-applicable is decided from positive data (Wikidata P452 industry in `nonDurableIndustries`); an unknown industry or a skipped/failed repair step yields `applicable`, never N/A. So N/A ≠ missing, and PLAN deliverable 2 requires exactly this redistribution. Oatly 35 (31.25/31.25/37.5) rather than 28 is the intended effect: a food brand is not structurally lower-scoring because an axis does not exist for it.
3. *Confidence rule* matches deliverables 2 and 3 (step `done` and at least one receipted signal, or a snapshot for track). Accepted. Documented asymmetry (LIMITATIONS): a completed regulator search with no ruling and no archive history counts as no track-record data (Mammut, Fairphone 70%). Fine for v1; Phase 7's live-vs-snapshot diff will give track data wherever Wayback answers.
4. *Claims axis from ClaimStats* follows ADR-015 (repeats count; supported 0.25 < unsupported 1); the `minWords` floor stops a short page inflating the rate. Note for Phase 9 LIMITATIONS: the rate's denominator is the fetched word count, so a page that fails to fetch can raise the claims rate; the brief prescribes the per-1,000-word normalisation, so this is a documented property, not a defect.
5. *No magic numbers*: clean. Nit, not a defect: `src/lib/claims/engine.ts` keeps `PER = 1000` for the displayed per-1,000 rates; it decides no points and the label is "per1000", so it may stay.
6. */methodology* renders the same `weightRows/pointRows/paramRows` the doc generator uses; `docs/METHODOLOGY.md` Section 7 is generated, not hand-copied. Good.
7. *Skipped items accepted*: the `signals` table is not required by any criterion (`ReportV1` holds the signals; Phase 8 decides whether to use or drop the table, and Phase 9 must not ship an unused table without a note). No report for a failed run is right: a failed run has no score to show; its could-not-check lines and timeline persist (Phase 4 carry-forward closed).
