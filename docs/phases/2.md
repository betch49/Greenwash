# Phase 2 — Page discovery, fetch, visible text, 3 fixture brands

Builder note, 2026-10-20.

## What was built

**Discovery (`src/lib/discover/`, `config/discovery.json`).**
- `sitemap.ts`: parses sitemaps and sitemap indexes (sitemaps.org 0.9, via cheerio's XML mode). `crawlSitemaps()` walks nested indexes breadth first, fetching at most `maxSitemaps` (10) documents and keeping at most `maxSitemapUrls` (200) accepted URLs. Child sitemaps whose URL looks like products, images, a blog or a shop are visited last.
- `heuristics.ts`: the 10 heuristic paths from the plan, the keyword weights, a locale-prefix splitter (`/da-dk/…`), and a same-site test that ignores `www.` (Oatly's sitemap lists `oatly.com` for the site `www.oatly.com`). `rankSitemapUrls()` keeps same-site, HTML-looking URLs whose locale-stripped path matches a keyword. It collapses translations of one page to one URL (no locale first, then English) and ranks by keyword weight minus a depth penalty, with deterministic tie-breaks. It keeps at most 3 deep URLs per first path segment. All weights and limits are in `config/discovery.json`.
- `discover.ts`: `discoverCandidates()` reads the `Sitemap:` lines of robots.txt (or falls back to `/sitemap.xml`) and orders the candidates: home page, then ranked sitemap matches, then heuristic paths. It dedupes them (bare host, path without trailing slash) and caps them at `maxFetchAttempts` (24).
- `fetch-pages.ts`: `fetchPages()` fetches candidates in order until 12 usable pages are collected (`maxPages`). It handles each result as follows:
  - 404/410: recorded as "not found". This is expected for heuristic paths and not shown as an error.
  - robots.txt disallows the URL: skipped with `robots.txt disallows <url>`, and the URL is never requested.
  - Fetch error, other HTTP status or non-HTML content: skipped with a reason.
  - Fewer than 50 visible words: skipped as too little text. This catches client-rendered shells and bot walls.
  - Visible text identical to an earlier page: dropped as a duplicate.
- `visible-text.ts`: `visibleText(html, baseUrl)` removes script/style/noscript/template/svg/iframe/select, hidden elements and site chrome (`nav`, `header`, `footer`, `aside` and their ARIA roles). It returns one line per block (headings, paragraphs, list items) with whitespace collapsed, plus `title`, `wordCount` and `links`. Links are absolute, have no fragment, and carry `region: content | chrome`. Chrome links are kept so that Phase 3 can still see a footer "Impact report" or "Factory list" link, but chrome text is never part of `text`.
- `robots.ts` now also parses `Sitemap:` lines (`RobotsChecker.sitemaps(origin)`).

**Robots guard wiring (ADR-010).** `guardedPageFetcher()` in `src/lib/pipeline/run.ts` wraps the cached, rate-limited fetcher (the fixture fetcher when offline) in `RobotsGuardedFetcher` for each run. Discovery, sitemap fetches and page fetches use only that guarded fetcher. No brand URL can reach the network without a robots check. The 1 req/s per-host limit comes from the Phase 1 `RateLimitedFetcher` (`GR_RATE_LIMIT_MS`, default 1000).

**Signal type (`src/lib/pipeline/signal.ts`).** `Signal` exactly as in the plan. `assertReceipt()` throws `ReceiptError` unless the signal has:
- an absolute http(s) `source_url`;
- an ISO date-time `fetched_at`;
- a non-blank `excerpt`.

`withReceipts()` filters a list on the same rules, and the pipeline applies it to every step's signals.

**Pipeline (`src/lib/pipeline/`).**
- `types.ts` defines `Step`, `StepResult` (`{ signals, skipped?, could_not_check, progress? }`) and `PipelineContext`.
- `steps/discover.ts` ("Discovering pages") and `steps/fetch-pages.ts` ("Fetching current pages") are the two steps. The fetch step adds one `Fetching <url>: skipped: <reason>` progress line per skipped page and a could-not-check entry for each robots-blocked URL. It also adds one when no sustainability-type page was fetched.
- `run.ts` (`runPipeline`) persists `runs.progress` after every change. A step that throws becomes `skipped: <message>` and the next step still runs.
- **Start rule (director note).** The pipeline never starts from a GET:
  - `/analyse/[runId]` renders the stored state.
  - A client component calls the `startRun` server action (POST) once on mount. A no-JS "Start analysis" form calls the same action.
  - `startAnalysis()` starts only after `RunsRepo.claimStart()`, an atomic `UPDATE … SET status='running' WHERE status='pending'`. So a refresh, a double submit or React strict mode cannot start a run twice.
  - A crawler that GETs `/confirm?q=…` can still create a pending run row (Phase 1 behaviour), but nothing is fetched.
- `/api/runs/[id]` (GET, read-only, `no-store`) returns status, progress and the fetched page list (URL, title, words, fetch date). The page polls it every 800 ms until the run is done.
- New table `run_pages` (bootstrap SQL kept in sync with Drizzle by the schema test) stores the fetched pages per run, with visible text, links and `fetched_at`, as the receipt source for later phases. `RunPagesRepo.replace/list`.

**UI.** `/analyse/[runId]` shows the brand facts, a live progress list (each line "done", "running…" or "skipped: reason") and, when finished, "Pages fetched (N)" with title, word count and fetch date. All strings are in `src/lib/copy/wording.ts` (`steps`, `reasons`, `couldNotCheck`, new `ui` keys). There is no horizontal overflow on a phone.

**Fixtures (`fixtures/brands/`, see its README).**
- **Fairphone** (electronics) and **Oatly** (food) are real captures recorded 2026-10-20 by `npm run record:brand`. The script runs the real discovery and fetch steps against the live sites (robots-guarded, 1 req/s, descriptive UA, normal TLS verification via the proxy CA) and saves every 2xx response.
  - At capture, inline script bodies are stripped, and Oatly's 9.7 MB sitemap is reduced to its 5,180 `<loc>` entries. Both changes are documented and leave the visible text unchanged.
- **Patagonia** (outdoor apparel) is **synthetic, hand-built**. Every request from this container to patagonia.com or eu.patagonia.com, including `/robots.txt`, returned a bot-protection page ("Hang Tight! Routing to checkout..."), and we did not try to get around it.
  - Every file is marked `synthetic fixture`, and the README states that the text is not a quote of Patagonia.
  - The fixture includes a nested sitemap index, a translation duplicate, a PDF entry, and a robots-disallowed `/stories/archive/our-footprint-2019/`.
  - It also includes nav/footer sentinels and claim sentences, report and supplier-list links, labels, and repair and warranty pages for Phases 3 and 5.
- Offline, `FixtureFetcher` reports each brand fixture's capture date as `fetched_at`, not the test time. It now takes a per-URL `fetchedAt` callback.

## Skipped / deviations, and why

- **Patagonia is synthetic** (bot wall, see above). The plan allows this ("otherwise synthetic, marked"). Offline-mode runs for "patagonia" therefore show hand-written text. Phase 8/9 should keep the offline mode clearly a test mode, and `docs/LIMITATIONS.md` (Phase 9) should say so.
- **Wayback fallback for robots-disallowed pages** (ADR-010, brief Section 8) is not done yet. The snapshot module is Phase 4. The fetch step already collects `ctx.robotsDisallowed` and lists each one under could-not-check, so Phase 4 can pull them from Wayback.
- **Wayback was unreachable from this container** (connection reset on `web.archive.org`) when I tried a CDX query. It is not needed in Phase 2, but it matters for Phase 4 fixtures (they are hand-built per the plan anyway).
- **`could_not_check` is returned by `runPipeline` but not yet persisted.** The report record that holds it arrives with the scorer and report (Phase 6). Pages, progress and status are persisted.
- **Discovery does not follow home-page links.** The plan specifies sitemaps plus heuristics only. Fairphone and Oatly expose almost nothing at the heuristic paths (only `/warranty` and `/sustainability`), so the keyword-ranked sitemap does most of the work.
- **The `GET /confirm` auto-proceed still creates a pending run row** (Phase 1 behaviour, director said it was harmless). It no longer matters because nothing fetches until the explicit POST start.
- **If the server restarts mid-run, the run stays `running`.** There is no resume yet. Acceptable for v1 and noted for Phase 9 limitations.
