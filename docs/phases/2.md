# Phase 2 — Page discovery, fetch, visible text, 3 fixture brands

Builder note, 2026-10-20.

## What was built

**Discovery (`src/lib/discover/`, `config/discovery.json`).**
- `sitemap.ts`: parses sitemaps and sitemap indexes (sitemaps.org 0.9, via cheerio's XML mode). `crawlSitemaps()` walks nested indexes breadth first, fetching at most `maxSitemaps` (10) documents and keeping at most `maxSitemapUrls` (200) accepted URLs. Child sitemaps whose URL looks like products, images, a blog or a shop are visited last.
- `heuristics.ts`: the 10 heuristic paths from the plan, the keyword weights, a locale-prefix splitter (`/da-dk/…`), and a same-site test that ignores `www.` (Oatly's sitemap lists `oatly.com` for the site `www.oatly.com`). `rankSitemapUrls()` keeps same-site, HTML-looking URLs whose locale-stripped path matches a keyword. It collapses translations of one page to one URL (no locale first, then English) and ranks by keyword weight minus a depth penalty, with deterministic tie-breaks. It keeps at most 3 deep URLs per first path segment. All weights and limits are in `config/discovery.json`.
- `discover.ts`: `discoverCandidates()` reads the `Sitemap:` lines of robots.txt (or falls back to `/sitemap.xml`) and orders the candidates: home page, then ranked sitemap matches, then heuristic paths. It dedupes them (bare host, path without trailing slash) and caps them at `maxFetchAttempts` (24).
- `fetch-pages.ts`: `fetchPages()` fetches candidates in order until 12 usable pages are collected (`maxPages`). It handles each result as follows:
  - 404/410: recorded as "not found". This is expected for heuristic paths and not shown as an error.
  - robots.txt disallows the URL: skipped with `robots.txt disallows <url>`, and the URL is never requested.
  - Fetch error, other HTTP status or non-HTML content: skipped with a reason.
  - Fewer than 50 visible words: skipped as too little text. This catches client-rendered shells and bot walls.
  - Visible text identical to an earlier page: dropped as a duplicate.
- `visible-text.ts`: `visibleText(html, baseUrl)` removes script/style/noscript/template/svg/iframe/select, hidden elements and site chrome (`nav`, `header`, `footer`, `aside` and their ARIA roles). It returns one line per block (headings, paragraphs, list items) with whitespace collapsed, plus `title`, `wordCount` and `links`. Links are absolute, have no fragment, and carry `region: content | chrome`. Chrome links are kept so that Phase 3 can still see a footer "Impact report" or "Factory list" link, but chrome text is never part of `text`.
- `robots.ts` now also parses `Sitemap:` lines (`RobotsChecker.sitemaps(origin)`).

**Robots guard wiring (ADR-010).** `guardedPageFetcher()` in `src/lib/pipeline/run.ts` wraps the cached, rate-limited fetcher (the fixture fetcher when offline) in `RobotsGuardedFetcher` for each run. Discovery, sitemap fetches and page fetches use only that guarded fetcher. No brand URL can reach the network without a robots check. The 1 req/s per-host limit comes from the Phase 1 `RateLimitedFetcher` (`GR_RATE_LIMIT_MS`, default 1000).

**Signal type (`src/lib/pipeline/signal.ts`).** `Signal` exactly as in the plan. `assertReceipt()` throws `ReceiptError` unless the signal has:
- an absolute http(s) `source_url`;
- an ISO date-time `fetched_at`;
- a non-blank `excerpt`.

`withReceipts()` filters a list on the same rules, and the pipeline applies it to every step's signals.

**Pipeline (`src/lib/pipeline/`).**
- `types.ts` defines `Step`, `StepResult` (`{ signals, skipped?, could_not_check, progress? }`) and `PipelineContext`.
- `steps/discover.ts` ("Discovering pages") and `steps/fetch-pages.ts` ("Fetching current pages") are the two steps. The fetch step adds one `Fetching <url>: skipped: <reason>` progress line per skipped page and a could-not-check entry for each robots-blocked URL. It also adds one when no sustainability-type page was fetched.
- `run.ts` (`runPipeline`) persists `runs.progress` after every change. A step that throws becomes `skipped: <message>` and the next step still runs.
- **Start rule (director note).** The pipeline never starts from a GET:
  - `/analyse/[runId]` renders the stored state.
  - A client component calls the `startRun` server action (POST) once on mount. A no-JS "Start analysis" form calls the same action.
  - `startAnalysis()` starts only after `RunsRepo.claimStart()`, an atomic `UPDATE … SET status='running' WHERE status='pending'`. So a refresh, a double submit or React strict mode cannot start a run twice.
  - A crawler that GETs `/confirm?q=…` can still create a pending run row (Phase 1 behaviour), but nothing is fetched.
- `/api/runs/[id]` (GET, read-only, `no-store`) returns status, progress and the fetched page list (URL, title, words, fetch date). The page polls it every 800 ms until the run is done.
- New table `run_pages` (bootstrap SQL kept in sync with Drizzle by the schema test) stores the fetched pages per run, with visible text, links and `fetched_at`, as the receipt source for later phases. `RunPagesRepo.replace/list`.

**UI.** `/analyse/[runId]` shows the brand facts, a live progress list (each line "done", "running…" or "skipped: reason") and, when finished, "Pages fetched (N)" with title, word count and fetch date. All strings are in `src/lib/copy/wording.ts` (`steps`, `reasons`, `couldNotCheck`, new `ui` keys). There is no horizontal overflow on a phone.

**Fixtures (`fixtures/brands/`, see its README).**
- **Fairphone** (electronics) and **Oatly** (food) are real captures recorded 2026-10-20 by `npm run record:brand`. The script runs the real discovery and fetch steps against the live sites (robots-guarded, 1 req/s, descriptive UA, normal TLS verification via the proxy CA) and saves every 2xx response.
  - At capture, inline script bodies are stripped, and Oatly's 9.7 MB sitemap is reduced to its 5,180 `<loc>` entries. Both changes are documented and leave the visible text unchanged.
- **Patagonia** (outdoor apparel) is **synthetic, hand-built**. Every request from this container to patagonia.com or eu.patagonia.com, including `/robots.txt`, returned a bot-protection page ("Hang Tight! Routing to checkout..."), and we did not try to get around it.
  - Every file is marked `synthetic fixture`, and the README states that the text is not a quote of Patagonia.
  - The fixture includes a nested sitemap index, a translation duplicate, a PDF entry, and a robots-disallowed `/stories/archive/our-footprint-2019/`.
  - It also includes nav/footer sentinels and claim sentences, report and supplier-list links, labels, and repair and warranty pages for Phases 3 and 5.
- Offline, `FixtureFetcher` reports each brand fixture's capture date as `fetched_at`, not the test time. It now takes a per-URL `fetchedAt` callback.

## Skipped / deviations, and why

- **Patagonia is synthetic** (bot wall, see above). The plan allows this ("otherwise synthetic, marked"). Offline-mode runs for "patagonia" therefore show hand-written text. Phase 8/9 should keep the offline mode clearly a test mode, and `docs/LIMITATIONS.md` (Phase 9) should say so.
- **Wayback fallback for robots-disallowed pages** (ADR-010, brief Section 8) is not done yet. The snapshot module is Phase 4. The fetch step already collects `ctx.robotsDisallowed` and lists each one under could-not-check, so Phase 4 can pull them from Wayback.
- **Wayback was unreachable from this container** (connection reset on `web.archive.org`) when I tried a CDX query. It is not needed in Phase 2, but it matters for Phase 4 fixtures (they are hand-built per the plan anyway).
- **`could_not_check` is returned by `runPipeline` but not yet persisted.** The report record that holds it arrives with the scorer and report (Phase 6). Pages, progress and status are persisted.
- **Discovery does not follow home-page links.** The plan specifies sitemaps plus heuristics only. Fairphone and Oatly expose almost nothing at the heuristic paths (only `/warranty` and `/sustainability`), so the keyword-ranked sitemap does most of the work.
- **The `GET /confirm` auto-proceed still creates a pending run row** (Phase 1 behaviour, director said it was harmless). It no longer matters because nothing fetches until the explicit POST start.
- **If the server restarts mid-run, the run stays `running`.** There is no resume yet. Acceptable for v1 and noted for Phase 9 limitations.

## Director review

**Verdict: REWORK** (review round 1 of 3, 2026-10-20).

Verified by the director on commit `fcaaf1c`: `npm run lint` clean, `npm run typecheck` clean, `npm test` 88/88 (16 files), `npm run test:e2e` 13/13 in Chromium (offline fixtures, fresh `test-results/e2e.db`), no skipped tests, servers stopped afterwards. Criteria 2.1–2.6 each map to a passing test as the builder's table states. The discovery, visible-text, sitemap, pipeline and start-rule work is good and is not the reason for the rework. The three defects below are about honesty of receipts and of failure states, which the brief ranks above features.

### Defects (fix all three; nothing else is required)

**1. The synthetic fixture impersonates a real brand.** `fixtures/brands/patagonia/` attaches hand-written sentences ("We are carbon neutral.", "Our packaging is 100% sustainable and completely natural.", "Our new shell fabric is more sustainable…") to real `https://www.patagonia.com/...` URLs and to the real Wikidata entity Q1660552 Patagonia, Inc. From Phase 3 on, every offline run and every test would produce *receipts* whose `source_url` is a real Patagonia page and whose `excerpt` Patagonia never published. That breaks brief Section 1 ("every signal has a receipt": a receipt is a real fetch), Section 8 ("any wording that states a fact about a brand that is not in a receipt") and Section 6 ("real saved HTML of 3 brands"). The `synthetic fixture` comment and the README do not cure it: the app's offline mode shows "Patagonia, Inc." with invented claims, and nothing in a report distinguishes them from a capture. The PLAN's "otherwise synthetic, marked" clause was written for an unreachable sector, not for fabricated text under a real brand's domain; ADR-011 closes that gap. Required:
   - a. Re-home the synthetic fixture under a **fictional** brand and a reserved domain (for example `Northwind Outdoor`, `https://www.northwind-outdoor.example`; any name that is not a real company, any `.example`/`.test`/`.invalid` host). `meta.json`: `capture: "synthetic"`, no Wikidata id, a fictional entity. Keep everything else (nested sitemap index, translation duplicate, PDF entry, robots-disallowed archive page, nav/footer sentinels, claim sentences, repair/warranty pages): it is a good test asset for 2.2, 2.4 and Phases 3/5. It is a fourth, test-only fixture, not one of the three brands.
   - b. Record a **real** outdoor-apparel brand with `npm run record:brand`. The director verified today through the container proxy, with the project User-Agent: **Mammut** (`www.mammut.com`: robots.txt 200, sitemap index 200 → `/int/en/sitemap.xml` lists `/us/en/responsibility`, `/us/en/responsibility-net-zero`, `/us/en/repair-and-care`, `/us/en/about-us`; `/us/en/responsibility` returns 200 with ~576 server-rendered visible words) and **VAUDE** (`www.vaude.com`: robots.txt 200, sitemap index 200 → `vaude_int_en.xml` with `equipment/spare-parts-repair` and `green-button` pages). Fjällräven (Cloudflare 403) and Picture Organic (429) are not usable. Record the Wikidata fixtures for the chosen query (`npm run record:wikidata` or the Phase 1 equivalent); note that `wbsearchentities` for "mammut" returns the extinct genus first, so the card path or a query such as "mammut sports group" may be needed, and either is fine for 2.6 (the e2e test already handles both branches).
   - c. Update `fixtures/brands/README.md`, `tests/unit/helpers/brands.ts` (2.1/2.3 parametrised over the three real brands; the fictional fixture may be added as a fourth entry or used only by 2.2/2.4), `tests/e2e/analyse-progress.spec.ts` (the robots-skip assertion and page-title assertion must use whichever fixture is run) and `tests/e2e/mobile.spec.ts` if it names Patagonia. Keep the Phase 1 "patagonia" Wikidata fixtures: offline, a "patagonia" run will honestly end with `skipped: no page could be fetched from www.patagonia.com`, which is the correct behaviour for a site that bot-blocks us.
   - d. Add a guard test (for example in `tests/unit/fetch/brand-fixtures.test.ts`): every fixture whose `meta.capture === "synthetic"` has a website host under a reserved TLD and no real Wikidata id; every `real` fixture's HTML files start with the `real capture:` comment. This test is what keeps ADR-011 enforced after this phase.

**2. The robots guard fails open.** `RobotsChecker.robotsFor` maps any fetch error and any non-2xx status to `EMPTY_ROBOTS`, i.e. "allow everything", and a 2xx HTML body (exactly what patagonia.com's bot wall returned for `/robots.txt`) parses to zero rules and also allows everything. RFC 9309 §2.3.1.3–2.3.1.4: 4xx ⇒ allow; 5xx or unreachable ⇒ treat as complete disallow (a cached copy may be used). Required: on a 5xx, a network error, or a 2xx whose content type is HTML or whose body starts with `<` (not a robots file), the checker disallows the whole origin with a reason via `wording.ts` such as `robots.txt unavailable for https://host (HTTP 503)`; discovery then skips the site with that reason (shown, never hidden). 404/410 and other 4xx keep allowing. Tests in `tests/unit/fetch/robots.test.ts`: 503 ⇒ disallowed, network error ⇒ disallowed, 200 HTML body ⇒ disallowed, 404 ⇒ allowed, and a `skip.test.ts` case showing the run line `skipped: robots.txt unavailable …`. Logged as ADR-012.

**3. An interrupted run stays `running` forever.** `/analyse/[runId]` would show "running…" indefinitely after a server restart, which is a hidden failure; brief Section 3.3 requires failed steps to appear as `skipped: reason`, never hidden. Minimal fix, no resume needed: when `toRunView` (used by the page and `/api/runs/[id]`) sees `status === "running"` and `inflightRun(run.id)` is undefined in this process, mark the run `failed`, turn the entry still marked `running` into `skipped: analysis interrupted (server restarted); search again to retry` (string in `wording.ts`), persist, and return that view. Unit test in `tests/unit/pipeline/start.test.ts`: `create` + `claimStart` with no pipeline ⇒ view status `failed` with that line; a run that this process is executing is left alone. The single-process assumption goes into `docs/LIMITATIONS.md` in Phase 9. Logged as ADR-013.

### Rulings on the open points

- **(a) Patagonia synthetic fixture:** not accepted with labelling; see defect 1 and ADR-011. Labelling protects the reader of the repo, not the user of the app, and the brief's receipts rule is about the user.
- **(b) `GET /confirm` creates an empty pending run row:** accepted, not a defect. The side effect is a database row; nothing is fetched until the explicit POST start, which the no-JS e2e test proves. Phase 8 makes it moot by serving a cached report for an already-analysed brand instead of creating a new run. ADR-013.
- **(c) Interrupted runs stay `running`:** defect 3 above (it hides a failure; the fix is small).
- **(d) Robots guard coverage:** the wiring is correct: `guardedPageFetcher` wraps the fetcher once per run and `discoverStep`, `crawlSitemaps` and `fetchPages` only ever receive `ctx.pageFetcher`, so no brand URL bypasses the check; robots.txt itself goes through the cached, rate-limited fetcher. The gap is the fail-open behaviour, defect 2.

### Non-blocking notes (no action required this round)

- `could_not_check` not persisted until Phase 6: fine, as long as the robots-blocked list survives into the report with its Wayback-fallback note (ADR-010).
- The 50-visible-words threshold for "too little text" is sensible; record it in `config/discovery.json` if it is not already there, so it is not a magic number when METHODOLOGY is written.
- Web.archive.org unreachable from the container: already expected by ADR-006; Phase 4 fixtures are hand-built by construction and, unlike brand pages, are diffs of *our* fixture text, so ADR-011 applies to them too: snapshot fixtures of a fictional brand, or real CDX/`id_` captures recorded when the host is reachable, never invented snapshots under a real brand's URL.

### 2. robots.txt fails closed (ADR-012)

`robotsFromResponse` in `src/lib/fetch/robots.ts`: 4xx ⇒ allowed; 2xx robots file ⇒ its rules; 5xx, any other
status, a network error, or a 2xx whose content type is HTML or whose body starts with `<` ⇒ the whole origin is
disallowed with the reason `robots.txt unavailable for <origin> (<cause>)` (`reasons.robotsUnavailable` in
`wording.ts`). The guard throws `RobotsUnavailableError` (a `RobotsDisallowedError`), so per-page skips are
shown too. `discoverStep` checks the website's origin first and, if unavailable, ends as
`skipped: robots.txt unavailable …` without requesting anything else; the origin is added to
"what we could not check". Tests: `robots.test.ts` (503, network error, HTML body with and without an HTML
content type, 401/403/404/410 allowed, guarded fetcher never requests the page) and `skip.test.ts` (run line
`skipped: robots.txt unavailable for https://www.northwind-outdoor.example (HTTP 503)`, only robots.txt requested).
Not done: ADR-012's "use a cached robots.txt when the live fetch fails" (the cached fetcher does not yet serve
stale entries on failure); the failure is shown, never hidden, so this only costs coverage. Noted for Phase 8.

### 3. Interrupted runs are shown as failed (ADR-013)

`settleInterrupted` in `src/lib/pipeline/start.ts`, called by `toRunView` (page and `/api/runs/[id]`): a run
with status `running` and no in-flight pipeline in this process is marked `failed`; the entry still `running`
becomes `skipped: analysis interrupted (server restarted); search again to retry` (`reasons.interrupted`), or a
`Pipeline` skipped line is added if no step was recorded; persisted. Tests in `start.test.ts`: claimed run with
no pipeline ⇒ failed + that line, persisted; empty progress ⇒ `Pipeline` line; in-flight, pending and done
runs untouched; default in-flight check uses `inflightRun`. The single-process assumption goes into
`docs/LIMITATIONS.md` in Phase 9.
