# Phase 8: Report UI, JSON export, shareable cached report, accessibility

Builder note, 2026-10-21.

## What was built

**Report page `/report/[id]`** (`src/app/report/[id]/page.tsx`). It is a server component that reads only the stored `ReportV1`. It shows:
- **Header:** the brand, its website, the Wikidata link, and the generation date. The P154 logo is shown only when the app is online (`!services.offline`) and only for an `https://` Commons URL. It is never shown from fixtures (Phase 1 carry-forward).
- **Headline:** the score out of 100, the label (Low/Moderate/High signals), "Based on N verified signals from M sources.", "Score N, confidence M%", "AI contributed to X% of this score", and a link to `/methodology`.
- **Summary:** the summary text with its AI note, or "Summary unavailable".
- **Four axes,** one `section[data-axis]` each. Each shows its sub-score, the configured and effective weight, the `axisStatus` wording (Phase 6 carry-forward) and its number of receipts. Each receipt row is an `li[data-signal]` with:
  - the label and the excerpt;
  - the source URL link, the fetch date, the archived-copy date and the `entity_name` when present;
  - an **AI-assisted** badge when `llm_used`;
  - its risk points from the scorer's own `signalPoints()`. Protective kinds are shown as "0 points (protective: listed, counts as data)" (ADR-020) and are never hidden. No number here is new: display only.
- **Timeline:** the shared `src/app/_components/timeline.tsx` (moved from /analyse). It includes the live row and "claim removed between <year> and the current page" (Phase 7 carry-forward).
- **What we could not check.** Possible regulator matches (lines starting with `POSSIBLE_MATCH_PREFIX`, now a constant in `wording.ts`) are split out under "Possible matches (not scored)" with the entity verbatim. They are never placed in the track-axis receipts (ADR-019).
- **Skipped steps:** "step: skipped: reason".
- **AI calls in this report:** the `llm_calls` log.
- **Share and export:**
  - the absolute page URL as the share link;
  - "Download evidence (JSON)" (`/api/reports/<id>.json`, `download` attribute);
  - "Re-run the analysis", a server-action form that also works without JS;
  - "Search for another brand".

**JSON export** (`src/app/api/reports/[file]/route.ts`): the stored JSON exactly as saved, served with `content-disposition: attachment`. Anything other than `<uuid>.json`, or an unknown id, returns 404.

**Serving from cache.**
- `ReportsRepo.findFresh()` and `src/lib/report/cache.ts` (`reportTtlHours`, `GR_REPORT_TTL_HOURS`, default 168; `freshReportId`; `websiteKeys`) back the cache. `src/lib/report/serve.ts` uses the pipeline clock, the same clock that stamps `generated_at`.
- The confident auto-proceed (`/confirm`), `confirmCandidate` and `startFromUrl` all redirect to a fresh report instead of creating a run.
- **Identity rule:** the same website (with or without a trailing slash) and the same Wikidata entity, or, for a pasted website, the same typed name. I found that matching on the website alone re-served an "acme"-named URL-fallback report for an "oatly" Wikidata search, which would show the wrong brand name and entity. So the identity rule is stricter than "same website", and the change is noted here and in LIMITATIONS.
- `next.config.ts` sets `x-gr-served-from: cache` on `/report/:id` and `/api/reports/:file`. Both always read the stored report.
- `/analyse` gains an "Open the full report" button when the run is done. The placeholder "full report arrives later" wording is gone.

**Stale robots.txt (ADR-012 amendment, LATER row closed).** When the live fetch fails (throws, 5xx or 429), `CachedFetcher` serves the last cached `/robots.txt` with its original `fetched_at`. Pages other than robots.txt are never served stale. With no cached copy, the origin is still skipped and the reason is shown.

**Northwind URL-fallback summary (ADR-021 carry-forward).** `scripts/author-llm-fixtures.ts` also authors the run "acme" + `https://www.northwind-outdoor.example`. This added one new file, `fixtures/llm/summary-0e6bfe4bcf9a.json`, a hand-authored stand-in. All existing fixtures were regenerated byte-identical. The offline flow now shows a summary for Northwind.

**CSS:** report styles in `globals.css`. Plain CSS, system fonts, light/dark through the existing tokens, no animations. The report page widens to 56rem on desktop and long URLs wrap.

**Lighthouse:** `npm run lighthouse` (`scripts/lighthouse.ts`, new dev dependencies `lighthouse` 13.5.0 and `chrome-launcher`).
- It starts `next start` offline on a throw-away database, drives Fairphone to a real report with Playwright's Chromium, and runs Lighthouse (accessibility category) through chrome-launcher on the same preinstalled binary (`/opt/pw-browsers/chromium-1194`). No `playwright install` was run.
- It writes `docs/phases/8-lighthouse.json`.
- **Result: 100 on `/`, `/confirm?q=continental`, `/confirm?q=acme`, `/report/[id]` and `/methodology`.** The report was re-served by the production server in 28 ms.
- Lighthouse ran, so the axe fallback was not needed. `tests/e2e/a11y.spec.ts` (`@axe-core/playwright`) runs anyway as a regression guard (0 serious/critical, light and dark).

`scripts/validate-report.ts` checks an exported file against `ReportV1Schema` with tsx. Playwright's loader cannot import the JSON config the schema depends on, so the export e2e test shells out to this script.

## Skipped / deviations, and why

- **Logo not covered by a test:** it renders only online and every test is offline by rule.
- **`x-gr-served-from: cache` is a route header,** not measured per request. Both routes only ever read the stored report, so the header is always true. The timing is measured in the tests.
- **Cache identity is stricter than "same website"** (see above). This is not a scope change: deliverable 2 says "a brand", and this rule makes the served report actually be that brand's.
- **`signals` table still unused:** the report page reads `ReportV1`. Phase 9 decides whether to drop it (Phase 6 review).
